Covers users, roles, links, Head Coach permission answers, weigh-ins, steps, sleep, measurements,
targets, meals, saved meals, workouts, settings, the AI consent record and the food list, plus the
sync bookkeeping. The MVP is the Personal Training User view only (D-20): links and
permission answers are post-MVP, but their tables stay in the schema so links can be added later
without rework. D- numbers refer to
[`owner-decisions-2026-10-27.md`](../product/owner-decisions-2026-10-27.md). The permission
matrix is in the [threat model](../security/data-and-threat-model.md#permission-matrix); it is
not repeated here.

## Conventions
- **Database:** Supabase PostgreSQL in Mumbai (ADR-0003). Only the Node API connects to it
  (ADR-0002).
- **Schema:** all tables live in a schema named `app`, not `public`, so Supabase's
  auto-generated Data API would not expose them even if it were turned back on. Every table also
  has row level security turned on with no policies, so Supabase's `anon` and `authenticated`
  roles can read nothing (ADR-0002 "second safety layer"). The API connects as the tables' owner.
- **Names:** tables are plural and `snake_case`. Primary keys are `id uuid`, generated by the
  database unless stated otherwise.
- **Time:** instants are `timestamptz`, stored and returned in UTC. A day the user chose is
  stored as its own `date` column holding an Asia/Kolkata (IST) day and is never derived from a
  timestamp (invariant #5, REQ-DATE-004).
- **Units:** one canonical unit per measure; conversion happens only for display and input
  (invariant #6). Body weight is stored as whole **grams**, sleep as whole **minutes**, and body
  measurements as whole **millimetres** (MVP defaults, D-23). Lifting weight is stored as whole
  **grams** too (REQ-TRN-005; MVP default, D-29).
- **Sensitivity:** columns marked **Health** hold sensitive data (REQ-NFR-002). They never
  appear in logs, analytics, error messages or fixtures; test data is synthetic (invariant #7).
  Database statement logging that captures values stays off (ADR-0003).
- **Changes:** every schema change is a numbered migration file in the repository, reviewed
  like code. Nobody edits tables by hand in the Supabase dashboard (D-16). The runner applies
  each file in one transaction and records it, with a checksum, in `app.schema_migrations`; a
  file edited after it was applied is refused (`apps/api/migrations/`, runbook).

## Entities

### `users`
One row per FitSphere account. Account data (threat model, "Assets").

| Column | Type | Rules |
|---|---|---|
| `id` | `uuid` | Primary key. FitSphere's own user ID; the sign-in provider's ID is never used as a foreign key (ADR-0002, ADR-0004 rule 3) |
| `auth_subject` | `text` | Not null, unique. The Supabase Auth user ID (the token's `sub` claim) |
| `email` | `text` | Not null, unique, stored lower-case. Copied at account setup from the Supabase Auth user record, which must show the email confirmed; never from a request body. Used later by invitations (REQ-ROLE-008, REQ-ROLE-009, T-05). Email change is not in the MVP |
| `age_confirmed_at` | `timestamptz` | Not null. Server time when the API received the "I am 18 or older" confirmation (REQ-ACC-010, D-18) |
| `age_confirmation_text_version` | `text` | Not null. Version of the confirmation text shown, e.g. `2026-10-27` (MVP default) |
| `created_at`, `updated_at` | `timestamptz` | Not null |

- A row exists only once the user has confirmed they are 18 or older: the two `age_` columns
  are not null, so the API cannot set up an account without the confirmation.
- Deleted by the delete-account flow (REQ-ACC-009, `DELETE /v1/me`; D-31), with everything that belongs
  only to the user.

### `user_roles`
The roles a user has turned on (REQ-ROLE-001). The active role is chosen on each device and is
not stored on the server; the server checks roles turned on, never the active role
(REQ-ROLE-002; Q-008 MVP default).

| Column | Type | Rules |
|---|---|---|
| `user_id` | `uuid` | References `users`, deleted with the user |
| `role` | `text` | One of `personal`, `coach`, `head_coach` |
| `turned_on_at` | `timestamptz` | Not null |

- Primary key: (`user_id`, `role`).
- Account setup turns on `personal` (Personal Training User) — MVP default, D-18.
- In the MVP no other role can be turned on: the role selector is hidden and no route turns on
  `coach` or `head_coach` (D-20, backlog B-17).
- Turning a role off is not in the Skeleton (backlog E-03). Turning on Coach or Head Coach gives
  no access to anyone's data (REQ-ROLE-001).

### `links`
An accepted link between two people (glossary: Coach record, Trainee record; D-10, D-11).

| Column | Type | Rules |
|---|---|---|
| `id` | `uuid` | Primary key |
| `kind` | `text` | `coach_trainee` or `head_coach_coach` |
| `upper_user_id` | `uuid` | References `users`. The coach (`coach_trainee`) or the Head Coach (`head_coach_coach`) |
| `lower_user_id` | `uuid` | References `users`. The trainee or the coach |
| `status` | `text` | `active` or `ended` |
| `started_at` | `timestamptz` | Not null. When the invitation was accepted |
| `ended_at` | `timestamptz` | Null while active |
| `end_reason` | `text` | Null while active; then `removed`, `left`, `switched` or `account_deleted` |
| `created_at` | `timestamptz` | Not null |

Integrity rules (ADR-0003):
- `upper_user_id` differs from `lower_user_id`.
- `status = 'active'` exactly when `ended_at` and `end_reason` are null.
- **One active link per lower user and kind**: a unique index on (`kind`, `lower_user_id`)
  where `status = 'active'`. A trainee has at most one coach and a coach at most one Head Coach
  (D-11).
- Ending a link — removal, leaving or switching — sets `status`, `ended_at` and `end_reason`;
  the row is never deleted (D-07).
- **Switching** (REQ-ROLE-015) is one transaction: end the old link with `switched`, then
  create the new one. If either step fails, neither happens.
- The API checks that the upper user has the matching role turned on (`coach` or `head_coach`)
  before creating a link.
- Links are post-MVP (D-20, backlog B-19). The table is created in the Skeleton so links can be
  added later without rework; in the MVP only ADR-0003's database tests write it. Invitations
  (REQ-ROLE-008, REQ-ROLE-009) are post-MVP too (backlog B-18).

### `head_coach_permission_answers`
A trainee's answers to "Allow Head Coach <name> to see your logs and set your plans and
targets?" (REQ-ROLE-013). Append-only: every answer and every change is a new row with its time.

| Column | Type | Rules |
|---|---|---|
| `id` | `uuid` | Primary key |
| `coach_trainee_link_id` | `uuid` | References `links` (kind `coach_trainee`) |
| `head_coach_link_id` | `uuid` | References `links` (kind `head_coach_coach`) |
| `answer` | `text` | `allowed` or `declined` |
| `answered_at` | `timestamptz` | Not null |

- The current answer is the latest row for the pair of links. No row means **pending** (not
  answered).
- Answers belong to that pair of links. A new coach link or a new Head Coach link starts with no
  answer, so answers never carry over (REQ-ROLE-013, REQ-ROLE-015).
- The API checks that both links share the same coach.
- Deleted with the trainee's account (Q-048 MVP default; Legal confirms, Q-049).
- Post-MVP (D-20, backlog B-20). In the MVP: the table only, with no route, screen or test
  fixture that writes it.

### `weigh_ins` — Health
One body-weight value per user per IST day (REQ-HOME-006, REQ-PRG-001).

| Column | Type | Rules |
|---|---|---|
| `id` | `uuid` | Primary key |
| `user_id` | `uuid` | References `users`, deleted with the user |
| `day` | `date` | Not null. The IST day the user chose (invariant #5). Not later than today in IST (REQ-DATE-001; Q-017 MVP default) |
| `weight_grams` | `integer` | Not null, **Health**. 20,000 to 300,000 (20–300 kg; Q-028 MVP default) |
| `recorded_at` | `timestamptz` | Not null. When the user saved it on the phone (UTC). Kept as a record; it does not decide conflicts |
| `change_seq` | `bigint` | Not null. Taken from the sequence `app.change_seq` on every insert and update; used by the sync pull |
| `created_at`, `updated_at` | `timestamptz` | Not null. Server times |

- Unique (`user_id`, `day`): a new value for a day replaces the old one, and the change the
  server receives last wins (Q-030 MVP default, ADR-0007 rule 2).
- Index (`user_id`, `change_seq`) for the sync pull.
- Nothing references `weigh_ins` by foreign key, so the table can later be partitioned by month
  without changing the app (ADR-0003).
- Who may read or write it: the
  [permission matrix](../security/data-and-threat-model.md#permission-matrix) (body metrics).
  The owner writes; their coach, and a Head Coach the trainee allows, read only (D-18). In the
  MVP only the owner reads or writes it (D-20).
- No delete in the Skeleton: no requirement asks for deleting a weigh-in. Deleted with the
  account (REQ-ACC-009).

| Column | Type | Rules |
|---|---|---|

| `user_id` | `uuid` | References `users`, deleted with the user |
| `day` | `date` | Not null. The IST day the user chose (invariant #5); not later than today in IST |
| `steps` | `integer` | Not null, **Health**. 0 to 100,000 (Q-028 MVP default) |
| `recorded_at` | `timestamptz` | Not null. When the user saved it on the phone (UTC) |
| `change_seq` | `bigint` | Not null. From `app.change_seq` on every insert and update |
| `created_at`, `updated_at` | `timestamptz` | Not null. Server times |

- Unique (`user_id`, `day`): a new value replaces the old, and the change the server receives

### `sleep_logs` — Health
One sleep value per user per IST day (REQ-HOME-006). The same columns and rules as `step_counts`,
with `sleep_minutes` in place of `steps`:

| Column | Type | Rules |
|---|---|---|
| `sleep_minutes` | `integer` | Not null, **Health**. 0 to 1,440 (0–24 h, Q-028). The app takes hours with one decimal, so values are multiples of 6 (MVP default, D-23) |

- The day is the date selected when the sleep is logged (MVP default, D-23).

### `measurements` — Health
One measurements entry per user per IST day (REQ-MEAS-001…006). The same `id`, `user_id`, `day`,
`recorded_at`, `change_seq` and server-time columns as `step_counts`, plus:

| Column | Type | Rules |
|---|---|---|
| `upper_waist_mm`, `lower_waist_mm` | `integer` | Not null, **Health**. Required (REQ-MEAS-004) |
| `chest_mm`, `hips_mm`, `arm_mm`, `thigh_mm` | `integer` | Null when not entered, **Health**. Optional (REQ-MEAS-005); one value each for arms and thighs (Q-027) |
| `notes` | `text` | Null when empty, **Health**. 1 to 500 characters (MVP default, D-23) |

- Every length is whole millimetres, 100 to 2,500 (10–250 cm, Q-028). The app takes cm or in with
  one decimal (REQ-MEAS-003, MVP default, D-23).
- Unique (`user_id`, `day`): a new entry replaces the whole old one, so an optional field left
  empty clears the old value (Q-030).

### `workouts` — Health
Workouts the user logs themselves (REQ-TRN-003, REQ-TRN-004; D-20). Unlike the day values, a day
may hold several workouts, and each with at least one exercise counts toward the weekly target
(REQ-HOME-007; D-41, replacing Q-025's default; MVP default, D-29).

| Column | Type | Rules |
|---|---|---|
| `user_id` | `uuid` | References `users`, deleted with the user |
| `id` | `uuid` | Made on the phone, so a workout can be started, edited and deleted offline. Primary key (`user_id`, `id`): an ID only ever names one user's workout, so no change can reach another user's workout (invariant #1) |
| `day` | `date` | Not null. The IST day the user chose when starting it (invariant #5); not later than today in IST. Kept after a deletion |
| `exercises` | `jsonb` | **Health**. An array of 0 to 30 exercises; null exactly when the workout is deleted |
| `recorded_at` | `timestamptz` | Not null. When the workout was started on the phone (UTC); editing it keeps this time |
| `timer_started_at` | `timestamptz` | **Health**. The workout timer (D-71): when "Start workout" was first tapped (UTC); null until then |
| `timer_counted_seconds` | `integer` | The time counted before the current run, 0 to 86,400; null exactly when `timer_started_at` is |
| `timer_running_since` | `timestamptz` | While the timer runs, when it was last started or resumed (UTC); otherwise null |
| `timer_done_at` | `timestamptz` | When the timer was marked done (UTC); otherwise null. Never set while `timer_running_since` is |
| `deleted_at` | `timestamptz` | When the user deleted it; null while it exists |
| `change_seq` | `bigint` | Not null. From `app.change_seq` on every insert and update |
| `created_at`, `updated_at` | `timestamptz` | Not null. Server times |

- Each exercise (D-50) has `name` (1 to 80 characters), `note` (1 to 500 characters, or null),
  `calories` (`{ kcal, estimated }`, 1 to 5,000 kcal, typed or estimated from the exercise list's
  MET, or null) and `averageHeartRateBpm` and `highestHeartRateBpm` (30 to 250, or null; the highest
  not below the average), and is one of two kinds:
  - `kind: 'sets'`: `sets`, 1 to 20 sets, each `{ reps, weightGrams, seconds }` with reps 1 to 200,
    `weightGrams` 100 to 500,000 (0.1–500 kg) and `seconds` 1 to 86,400, each or null, but reps or
    seconds in every set; and `durationSeconds`, the time spent (1 to 86,400, or null), used only to
    estimate calories.
  - `kind: 'cardio'`: `durationSeconds` (1 to 86,400), `distanceMetres` (10 to 500,000),
    `speedMetresPerHour` (100 to 40,000), `inclinePermille` (tenths of a percent, 0 to 400) and
    `level` (1 to 40), each but the time or null.
  The API checks these; the table checks the array. An exercise saved before D-50,
  `{ name, sets, reps, weightGrams, note }` with the same reps and weight for every set, is read and
  served as that many identical sets; a change from an older app in that shape is stored in today's.
  Workouts keep each exercise's name, not a link to the exercise list.
- A new change for the workout replaces the whole workout, and the change the server receives
  last wins, also over an earlier deletion (ADR-0007 rule 2).
- **The timer** (D-71, migrations 0025 and 0026): the four `timer_` columns are all null, or the timer has
  started with a count; running (`timer_running_since` set), paused (neither set) or done
  (`timer_done_at` set). Its time is the count plus the time since `timer_running_since`, at most 24
  hours, worked out on the phone. In changes and the pull it is one field, `timer`: `{ startedAt,
  countedSeconds, runningSince, doneAt }` or null; a `workout.set` without it, from an app before
  D-71, keeps the timer stored.
- **Deleting** empties `exercises` and the timer and sets `deleted_at`, keeping the row and its day,
  so the user's other phones learn of the deletion at their next sync.
- Indexes (`user_id`, `change_seq`) for the sync pull and (`user_id`, `day`) for the history.
- Who may read or write it: the
  [permission matrix](../security/data-and-threat-model.md#permission-matrix) ("Workouts and
  Progress"). In the MVP only the owner reads or writes it (D-20).

### `targets` — Health
The user's own targets (REQ-ROLE-007, D-20), by date (D-77, answering Q-014): each value holds from
its IST `day` until the next value of that kind, so a change never rewrites the days before it, and
the values kept are the user's target history (REQ-ROLE-018). They include a target body weight, so
the values are treated as **Health** data.

| Column | Type | Rules |
|---|---|---|
| `id` | `uuid` | Primary key |
| `user_id` | `uuid` | References `users`, deleted with the user. Whose target it is |
| `kind` | `text` | `calories`, `protein`, `carbs`, `fat`, `fibre` (D-70), `steps`, `weekly_workouts` or `body_weight` (check `targets_kind`, migration 0024) |
| `day` | `date` | Not null. The IST day the value starts (D-77): the day it was set on the phone, kept as its own field (invariant 5), never later than today. Migration 0027 gave the rows already there the IST day their user's account was created |
| `value` | `integer` | Not null. kcal 500–10,000; protein in grams 10–500; steps 1–100,000; workouts a week 1–14; body weight in grams 20,000–300,000 (MVP defaults, D-23; Q-028); carbs in grams 10–1,000, fat 5–500, fibre 5–100 (D-70) (check `targets_value`) |
| `set_by_user_id` | `uuid` | References `users`, `on delete set null`. Who set it: always the caller, from the sign-in token, never from the request. Null only once that person's account is deleted (backlog E-02) |
| `set_at` | `timestamptz` | Not null. When it was set, on the phone (UTC) |
| `change_seq` | `bigint` | Not null. From `app.change_seq` on every insert and update |
| `created_at`, `updated_at` | `timestamptz` | Not null. Server times |

- Unique (`user_id`, `kind`, `day`) (`targets_user_kind_day`, migration 0027): a second value the
  same day replaces that day's, and the change the server receives last wins (Q-075); a value for
  another day is kept beside the others. The target on a date is the value of that kind with the
  latest `day` on or before it; none means no target that day. Home's workout tracker reads a week's
  on its Sunday (D-77). Replaces D-23's one value per kind, applying to every day shown.
- In the MVP every target is set by its user (D-20), labelled "Set by you". Recording who set it
  lets coach-set targets follow without rework (invariant #2): post-MVP, the API refuses a
  trainee's change while an active coach's target applies (backlog B-21).
- A target can be changed but not removed in the MVP (D-23).

| `sex` | `text` | **Health.** `female`, `male`, `other` or `prefer_not_to_say`, or null |
| `height_mm` | `integer` | **Health.** Whole millimetres, 1,000 to 2,500 (100–250 cm; invariant #6), or null |
| `phone` | `text` | **Contact.** `+91` and a 10-digit Indian mobile number (first digit 6 to 9), or null. Not verified |
| `address_line1`, `address_line2`, `city`, `state`, `pin_code` | `text` | **Contact.** All null, or line 1 (1–100 characters), the city and the state (1–60 each) and a 6-digit PIN code; line 2 (1–100) optional |

| `set_at` | `timestamptz` | Not null. When it was saved, on the phone (UTC) |

### `meals` — Health
The user's logged meals (REQ-LOG-001…003, REQ-LOG-007, REQ-NUT-*). Migration 0004.

| Column | Type | Rules |
|---|---|---|
| `user_id` | `uuid` | References `users`, deleted with the user |
| `id` | `uuid` | Made on the phone, so a meal can be created, edited and deleted offline |

### Ordering rule for synced data
Any transaction that writes a user's synced data first locks that user's `users` row
(`SELECT … FOR UPDATE`). A user's `change_seq` values therefore commit in order, and a pull that
reads "everything after `change_seq` N" cannot miss a row that commits later with a smaller
number.

## On the phone (ADR-0007)
The phone keeps a **copy** in an encrypted Expo SQLite database; the server is the permanent
record (D-14). The key is a random value kept in the phone's secure storage; the user never sees
a password (ADR-0007 rule 5). The key is 32 random bytes from `expo-crypto`, used as a raw
SQLCipher key; the database file is `fitsphere.db`, and `PRAGMA user_version` numbers its schema.

Encryption uses SQLCipher, which needs a development build, not Expo Go. Expo's docs warn that
if SQLCipher is missing from the build, setting the key "has no effect and does not throw an
error". The app therefore checks at start that SQLCipher is active and does not open the
database unencrypted. If that check fails on a phone, it is raised with the owner, as ADR-0007
rule 5 and D-14 require.

Once the key is set, the connection keeps up to 8 MB of the database in memory, read and decrypted
(`PRAGMA cache_size = -8192`, D-74), so the whole food list a search reads stays there between
searches. The setting lasts as long as the connection and is set at each start.

- **What is kept:** the user's own weigh-ins, steps, sleep, measurements and workouts for the last
  90 IST days, and every target value (D-77) and their settings (ADR-0007 rule 1). Synced day entries older
  than that are deleted from the phone at each sync; targets and settings are never pruned. Older history is read from the
  server when viewed online.
- **Schema versions:** `PRAGMA user_version` counts the local migrations, applied one at a time,
  each in a transaction. Version 2 (Home and daily tracking slice) adds `steps`, `sleep`,
  `measurements` and `targets`, keeps everything already on the phone, and clears the sync cursor
  so the next sync pulls the new kinds.
- **Matching a change to its entry:** an outbox change is matched by its kind's change types and
  its key (`day`, `kind` and `day` for targets (D-77), `name` for settings, `id` for meals, saved meals and
  workouts, whose saves and deletions both count), so a waiting weight never holds back the server's steps for the same
  day, and a waiting deletion is never undone by the pull.
- **Deletions in the pull:** a meal, saved meal or workout the server marks `deleted` is removed
  from the phone, unless a change for it is still waiting.
- **Version 3** (Meal logging slice) adds `meals`, `saved_meals` and `foods`, keeps everything
  already on the phone, and clears the sync cursor so the next sync pulls the meals.
- **What is kept (meals):** the last 90 IST days of meals, like other day data; saved meals and
  the food list are always kept.
- **Version 4** (Meal logging slice) adds `meals.photo` and `photos`, and clears the sync cursor
  so the next sync pulls the meals' photos.
- **Version 5** (Meal logging slice, step 8; D-28) adds `dishes`, and clears
  `food_list_version` so the next download brings the dishes.
- **Version 6** (Training slice, D-29) adds `workouts` and clears the sync cursor so the next
  sync pulls them.
- **Version 7** (Settings slice, D-31) adds `settings` and clears the sync cursor so the next sync
  pulls the settings the account already has.
- **Version 8** (household units, D-36) adds `foods.measures`, each food's units and the grams one
  holds, and clears `food_list_version` so the next download brings them.
- **Version 10** (more foods, D-39) adds `foods.portions` (a USDA food's servings) and `my_foods`,
  and clears `food_list_version` and the sync cursor, so the next download brings USDA's foods and
  the next sync the user's My foods. The food list is written 50 rows a statement.
- **Version 11** (packaged foods, D-48) adds `packaged_foods` (barcode, name, brand, the five values
  per 100 g, serving grams), filled with the food list, and clears `food_list_version`, so the next
  download brings them.
- **Version 12** (brand labels, D-49) makes `foods` again with `fibre_g` allowed to be null (a brand
  label that gives no fibre), and clears `food_list_version`, so the next download fills it.
- **Version 13** (the exercise list, D-50) adds `exercises` and clears `exercise_list_version`, so
  the next download fills it. Workouts keep their exercises as JSON; one saved before D-50 is read as
  identical sets.
- **Version 14** (speed bands, D-50) adds `exercises.speed_mets` (JSON) and clears
  `exercise_list_version`, so the next download brings them.
- **Version 15** (ready-made search text, D-66) adds `foods.search_name`, `foods.search_aliases`,
  `packaged_foods.search_name` and `packaged_foods.search_brand`: the name, the aliases and the brand
  as Search foods reads them (lowercase, ' ’ . dropped, - & , / ( ) " read as spaces, after a space),
  written with each row when the list is stored, so a search does not work them out again for every
  food. The update fills them from the rows already on the phone and keeps `food_list_version`, so
  search keeps working offline and nothing is downloaded again. The packaged foods are written 90
  rows a statement. My foods and dishes, a few rows each, are read the same way at search time.
  Since D-86 and D-88 the search text has accents taken off and every mark but % read as a space.
- **Version 16** (the exercise library, D-67) adds `exercises.places` (JSON) and `exercises.place_keys`
  and clears `exercise_list_version`, so the next download brings them. The list is written 80 rows a
  statement.
- **Version 17** (saved meals keep no meal, D-69) makes `saved_meals` again without `meal_type` and
  copies every saved meal into it, those waiting to sync too.
- **Version 19** (targets by date, D-77) makes `targets` again keyed by kind and day. A target
  waiting to sync (or refused) keeps its value, from the IST day it was set, and its change in the
  outbox gets that `day`; the synced ones are dropped and the sync cursor cleared, so the next sync
  pulls every target value with its day.
- **Version 20** (an exercise's page, D-82) adds `exercises.details` (JSON, null when the library has
  none) and clears `exercise_list_version`, so the next download brings them.
- **Version 21** (accents ignored, D-88) clears `food_list_version`, so the next download writes every
  food's and packaged food's search text again, accents taken off. The foods stay on the phone and are
  searched with their old search text until then.
- **Version 22** (other names for packaged foods, D-94) adds `packaged_foods.aliases` (JSON, `[]` until
  the list comes) and `packaged_foods.search_aliases` (as a search reads them) and clears
  `food_list_version`, so the next download brings them. The products stay, searched by name and brand
  until then.
- **Version 9** (the profile, D-38) adds `profile` and clears the sync cursor so the next sync
  pulls the profile the account already has. A profile change is matched in the outbox by its type
  alone, there being one profile.
- **Photos** (REQ-LOG-006; D-14): a new photo is saved in the same transaction as the meal that
  names it. It is uploaded after a sync once its meal's change has been accepted; until then it
  counts as unsynced (the log-out warning includes it) and is never cleared automatically, and
  a meal whose photo waits is not pruned. A photo no meal names any more — the meal deleted here
  or on another phone, its photo replaced or removed, the change discarded, or the meal pruned —
  leaves the phone at once.
- **Never deleted automatically:** `pending` and `rejected` entries and their outbox rows
  (D-14). A rejected change stays visible until the user fixes or discards it (ADR-0007 rule 2).
- **30-day clear** (ADR-0007 rule 4): in the Skeleton there are no drafts and no other people's
  data on the phone, so nothing is cleared yet. The check is built with the first slice that
  stores either.
- **Discarding a rejected change** removes it and that entry's local value, and clears the sync
  cursor, so the next sync brings back what the server holds for it.
- **Log out** (REQ-ACC-008; MVP default, D-18): when the outbox is empty, logging out deletes the
  local database and its key. When it is not, the app warns that the unsynced entries will be
  lost and offers to stay signed in; the entries are deleted only if the user confirms.
